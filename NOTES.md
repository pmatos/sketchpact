# Sketchpact devlog

## M1: canvas + state server + sync
- Server: plain `http` + `ws` on 127.0.0.1. `GET/PUT /api/scene`, `/ws`, `/health`. Persists to `.sketchpact/canvas.excalidraw` (atomic tmp+rename). Port 3210, falls back to a random port; `.sketchpact/server.json` records the actual one.
- Tested at the server's HTTP+WS seam only (vitest, real server on port 0): health, empty scene, PUT + restart persistence, WS initial scene + relay to other clients, API writes pushed to WS clients.
- Web: Vite + React + `<Excalidraw/>`. Debounced (250ms) push of elements over WS; remote updates applied with `updateScene`. The Vite dev server proxies `/api` and `/ws`; the built app is served by the canvas server from `dist/web`.
- Surprise: Excalidraw loads fonts from a CDN by default, which breaks the no-internet constraint. Fix: `EXCALIDRAW_ASSET_PATH=/excalidraw-assets/` (set in its own module because ES imports are hoisted) and fonts copied from `node_modules` by `scripts/copy-assets.mjs` (postinstall). Verified: zero non-local requests on page load.
- Verified in a browser: seeded scene renders; dragging a shape pushes to the server and `customData.sketchpactId` survives the round trip (the sticky-id plan works).
- Known gap: last-writer-wins on the whole element array. Fine for turn-taking (one editor at a time), revisit if M6 needs concurrent editors.

## M2: semantic scene, diff, formatters (`src/shared`)
- Tested at three function seams (`extractScene`, `diffScenes`, `formatScene`/`formatDiff`) with hand-built element fixtures in `test/fixtures/elements.ts`. 28 tests total.
- Id decision: semantic id = `customData.sketchpactId`, falling back to the Excalidraw element id. Excalidraw ids are already stable across edits, so user-drawn shapes need no id assignment. The "sticky ids" idea reduces to "ops stamp the agent's chosen id into customData". Simpler than planned.
- Clusters: a frame is a cluster. A group counts only if it has 2+ shapes (a shape and its bound label share a `groupIds` entry, so a lone shape's group is noise). Nested groups resolve to the outermost id. A frame wins over a group.
- Warnings (`unlabeled`, `unbound start/end`) live in the scene and are diffed as added/removed, so the agent hears about half-drawn arrows the user leaves behind. An arrow bound to a non-node (e.g. a text note) counts as unbound.
- Diff ignores geometry and style entirely (test: move + recolor + resize yields an empty diff). A shape kind change (rect -> ellipse) is deliberately not reported.
- Diff output format is line-based rather than YAML (`+node`, `-node`, `~node`, `~edge`, `>node` for cluster moves, `!warning`), which is the cheapest thing that reads unambiguously.
- Dead end: my first edge test failed after adding warnings because its fixture had unlabeled nodes. The behaviour was right, the fixture was sloppy. Fixed the fixture.
- Not covered yet: text bound to arrows inside frames, arrows connected to frames, elements with `frameId` pointing at a deleted frame (treated as no cluster).

## M3: ops, MCP server, auto-start
- Tested at two seams: `applyOps(elements, ops)` (pure, observed through `extractScene`, 19 tests) and the real MCP server over stdio via the SDK client against a temp project dir (6 tests). Total 53.
- Architecture: the MCP server is a thin client. Ops are applied **in the canvas server** (`POST /api/ops`) so there is one writer, persistence and WS broadcast come for free, and the browser never sees a half-applied batch. `get_scene` and `apply_ops` fetch `/api/scene`, run `extractScene`/`diffScenes` locally and format the result.
- `apply_ops` is atomic: ops apply to a clone, and any failure discards the whole batch. Later ops in a batch can use ids from earlier ones. Errors are per-op (`op 1: unknown node "ghost"`).
- Auto-start: `ensureCanvas` reads `.sketchpact/server.json`, health-checks it, and otherwise spawns a detached server (`node --import tsx src/server/main.ts`) guarded by a `start.lock` file so two MCP sessions racing don't start two servers. Every tool calls it, so `open_canvas` is optional.
- Tool surface: still the 3 of the planned 6. `get_diff`, `yield_turn`, `save_decision` come with M4/M5.
- Cut: `add_cluster` only makes frames, no `type: "group"`. An empty group can't exist in Excalidraw (a group is just a shared `groupIds` entry), so it would need a member first. Users can still draw groups and `extractScene` reads them; `move_to_cluster` only targets frames.
- Removing a node removes its edges and labels; removing a frame releases its members instead of deleting them (Excalidraw's own behaviour would delete children).
- Excalidraw gotchas: programmatic elements need every field, and `updateScene` does not fill them in. The web app runs `restoreElements` on incoming scenes. Bound text needs both `containerId` on the text and a `boundElements` entry on the container, otherwise arrows and labels detach on drag. Text elements are not re-measured on load, so a too-small width clips the label; my first 9px/char estimate clipped everything, 12px/char fits Excalifont.
- Layout: grid slots (270x130 cells, first free), frames go to the right of existing content and grow to fit their members. `moveNode` re-anchors connected arrows and recentres their labels. Known weakness: no edge routing, so arrows can cross unrelated nodes (in the demo, web -> api crosses db). This is the case for elkjs later.
- Surprise, and the best anecdote so far: the first real Claude Code run (`claude -p` with `--mcp-config .mcp.json`) hit a leftover `api` node from my M1 test seed. `add_node` was rejected as a duplicate, and Claude read the error and recovered on its own by renaming the existing node. The duplicate-id guard and the readable error message did their job with no prompting.
- Gotcha: the detached canvas server keeps running old code after edits (tsx doesn't watch). I burned a screenshot round on stale constants. When developing, kill the pid in `.sketchpact/server.json`.
- Registered via project-level `.mcp.json`. `SKETCHPACT_ROOT` defaults to the cwd, so decision records will land in whichever project Claude Code is opened in.

## M4: turn-taking (`yield_turn`, side panel, snapshots)
- Tested at three seams: the server's turn API (real server on port 0, 11 tests), `yield_turn`/`get_diff` over MCP stdio (4 new tests, timeout shortened via `SKETCHPACT_YIELD_TIMEOUT_S=0.3`), and a committed Playwright test that drives the real panel in headless Chromium (1 test). 69 tests total.
- Snapshot semantics (the part worth explaining in the post): a turn's snapshot is taken **when the agent yields**, i.e. "the board as Claude left it". When the user presses a button, the diff is `diff(agent snapshot, board now)`, which is exactly the user's edits, with no bookkeeping of who changed what. `turns/NNN.json` holds `{agent:{message, elements}, user:{kind, comment, elements}}`, so a session is replayable and `get_diff(since_turn)` is just another diff against a stored snapshot (turn 0 = empty board).
- Long-poll: the yield call is an HTTP request held open by the canvas server (default 90s, `SKETCHPACT_YIELD_TIMEOUT_S`, clamped to 240s because Node's fetch gives up on headers after 300s). On timeout it returns `still_waiting` and the turn **stays open**; the agent calls `yield_turn` with no message to re-attach. Design rules that fell out of the tests:
  - Re-yielding with a message while a turn is open updates the message and snapshot instead of opening turn N+1, so a retry never double-counts.
  - A button press with nobody waiting (the agent's call timed out and hasn't re-attached yet) is stored and delivered exactly once to the next message-less yield, so a slow agent can't lose the user's answer. A second such call is a 409.
  - Turn numbers survive restarts (max of the filenames in `turns/`); an open turn does not, and the agent just yields again.
- WS protocol grew a second message type (`turn`), sent on every change and on connect, so a refreshed tab restores the panel. That broke two M1 tests that assumed the second WS message was a scene; they now wait for `type: "scene"`. A useful reminder that protocol changes belong in the tests too.
- Panel: plain React, no state library. Buttons and the comment box are disabled unless the phase is `user`; phases are `idle`, `user`, `agent`, `agreed`.
- Tool surface is now 5: `open_canvas`, `get_scene`, `apply_ops`, `yield_turn`, `get_diff`. Justification for `get_diff` (the one addition over the plan's list of six, which had it too): the agent can check "what changed since I last looked" mid-turn without yielding, and after a `still_waiting` it can inspect edits made during the wait.
- Testing note: vitest's `expect` doesn't retry Playwright locators, so the UI test uses `expect.poll`. `playwright-core` (no browser download) plus the Chromium revision already in `~/.cache/ms-playwright` is enough; `beforeAll` runs `vite build` so the test always exercises current UI code.
- Several M4 server tests passed on first run because the implementation was written to satisfy them in the same sitting; I kept them because they pin the behaviour (re-attach, held response) that would be easy to break later.
- Known cosmetic issue, timeboxed and left: the initial viewport does not zoom to fit wide diagrams (I tried `initialData.scrollToContent`, a delayed `scrollToContent`, and `scrollToContent({fit})` on API ready; the screenshot never changed). Users can pan/zoom. Revisit if it annoys during the real session.

## M5 (part 2): the first real session and the layout postmortem
- **The first live grill session produced an unreadable board.** The skill worked end to end (opened the canvas, drew a 17-op proposal, yielded turn 1), but the user's first note was: "This diagram is all clobbered and I can't read anything. This should never be presented as is." The screenshot and the exact ops are kept as regression data: `docs/session-1/turn1-unreadable.excalidraw`, `test/fixtures/screenshot-ops.json`.
- Honest root cause: in M3 I wrote down "no edge routing, arrows can cross unrelated nodes" as a known weakness and moved on. Labels overflowed fixed 160x80 boxes, arrows were straight lines through unrelated nodes, and edge labels sat on top of nodes and each other. The agent did nothing wrong; the tool let it present garbage. Lesson for the post: **a tool that lets an agent present something unreadable is a bug in the tool, not in the prompt.**
- What I built, in the order the tests forced it:
  1. `layoutIssues(elements)`, a pure readability checker: `text-overflow`, `overlap`, `edge-crosses-node` (shapes and notes), `label-collision` (shapes, notes, other labels, other edges), `detached-edge`, `too-large`. First test: run it on the real board from the session and require it to flag the same three problems I could see.
  2. Node sizing: labels word-wrap (18 chars for nodes, 14 for 16px edge labels) and shapes grow to fit, with less usable area assumed for ellipses (0.7) and diamonds (0.5). `originalText` now carries the unwrapped label so the semantic scene never sees wrap newlines. That's what real Excalidraw edits do too, and a test that simulated a user edit by changing only `text` failed until I fixed the simulation.
  3. `autoLayout` with elkjs (runs locally, pure JS): layered layout, hierarchical clusters, orthogonal routed edges, ports so arrows attach to shape outlines.
  4. Policy, chosen by the user: re-lay-out the whole board after each `apply_ops` **only if nobody rearranged it** (a hash of shape positions is stored in `.sketchpact/layout.json`); once the user drags or adds anything, fall back to incremental placement and never touch their arrangement, unless the agent sends an explicit `{op:"layout"}`.
  5. The gate: `yield_turn` refuses while `layoutIssues` is non-empty. If the mess is the agent's, it must fix it. If it is the user's own arrangement, the agent may present it only with `allow_layout_problems: true`, and the skill tells it to say so.
- **Every "clean" result I got was wrong at least once before it was right.** Worth telling in the post because it is the real process:
  - The checker reported the new layout as clean while the picture was a mess. I only saw it by rendering. Fit-to-screen (Shift+1) showed a 5000px-wide strip at 20% zoom. That led to the `too-large` check (whole board fitted to a 1200x850 canvas must render at >= 45% zoom, i.e. ~9px text).
  - ELK's `MULTI_EDGE` wrapping "fixed" the width but corrupted edge routes: `verdict -> cex-corpus` started at (210,170), nowhere near `verdict`. My checker did not check attachment at all. Added `detached-edge`, then dropped wrapping entirely.
  - The unit tests passed the good layout while the live server produced the bad one, because the server always passed `direction: RIGHT` (my persisted default), so it never considered the top-to-bottom candidate the unit test exercised. Fix: direction is only pinned once the agent asks for it, plus a regression test that runs the real session graph through the real MCP server path. Lesson: test at the seam the user actually hits.
  - Edge labels each become an ELK layer, so five labels doubled the width. Smaller edge labels and tighter spacing presets helped; the search now tries 3 spacing presets x {RIGHT, DOWN} and picks the candidate with the fewest issues, then the best fit scale (bucketed in 5% steps so roomier spacing wins ties).
- **Viewport bug that had been "cosmetic" since M4: the option is `fitToContent`, not `fit`.** All my earlier `scrollToContent` attempts silently did nothing because Excalidraw ignores unknown options. Found by exposing the API on `window` and evaluating in the browser. Now the whole board is fitted on load and every time the agent yields (Playwright test with a 4000px-wide board).
- Bug from my own tooling, for the record: a `str.replace` range that I meant to replace the ops handler also deleted the turn and diff endpoints between it and `/api/scene`; the test suite (19 red) caught it immediately. I also once ran `pkill -f` with a pattern that matched its own shell.
- Result on the real graph (7 nodes, 9 edges, 7 labels): 870x1712 top-to-bottom flowchart, fit scale 0.50, zero issues. Still tall: dense graphs with feedback loops are simply big. The skill now tells the agent to keep boards under ~10 nodes.

### Session 1 (retry): result
- Same design question as the unreadable attempt, on the fixed tooling. The board came out readable (fit at 80% zoom, every label legible) and the user answered in the panel and pressed **Agree** on turn 1. The agent then called `save_decision`; `docs/decisions/0001-solver-counterexamples-feed-the-test-corpus-unknown-is-rejec.{md,excalidraw}` are committed as the worked example.
- The long-poll did its job: the agent looped on `yield_turn` (no message) through 25 consecutive `still_waiting` results (~90s each, ~35 min of the user thinking) without losing the turn, complaining, or editing the board. It narrated "still waiting" only every 6 calls or so, which is the right amount.
- The record is good: it included rejected options with reasons, honest consequences, and an explicit "deferred, not discussed" list (retry budget, timeout values, per-function corpus) rather than pretending the design was complete. It also quoted the user's own phrasing.
- What the session did **not** exercise: the revise loop. The user agreed at turn 1, so the diff-driven "respond to my edits" path has only been tested by unit tests, not live. Next real run should be a design the user disagrees with.
- Gap found in the saved artifact: the diagram still contains the note "Open: on SAT, does the counterexample join the test corpus?" and has no corpus node, although the decision answers exactly that. Fixed in the skill (step 7: make the board show the decision before asking for agreement; resolve answered open notes; yield again if the board changes after agreement). Not fixed in the committed example on purpose: it is the evidence for this note.
- Small quality nits, not fixed: `Source asm fn` sits mid-diagram because ELK layers around feedback loops; edge routes for back edges are long.

### UX finding from the first real session: "Agree" was ambiguous
- The user pressed **Agree** meaning "yes to your recommendation" and did not realise it ends the session and triggers the decision record ("Oh - so Agree means design is finished."). The agent had asked "Agree?" about a single point, so the button label invited exactly that reading.
- Fix, in both places it went wrong: the button is now **Agree & finish** with a two-line explanation under the buttons, and the skill forbids phrasing questions as "Agree?" and tells the agent to announce explicitly when it thinks the design is final. It also tells the agent not to save when `agreed: true` arrives with a comment that still reads like a partial answer.
- Takeaway for the post: turn-taking protocols need a distinct "I'm done" signal and a distinct "continue" signal, and the UI has to name them by their consequence, not by their sentiment.

## M6: two agents with opposing mandates, the user as arbiter
- **Design decisions, chosen by the user:** a round waits for *both* agents before the arbiter can respond, with a "Don't wait for X" override so a dead agent can't deadlock the session; one scribe agent (first to register) writes the record; tests at three seams (`applyOps` with an actor, the server's round API, two real MCP sessions over stdio). No committed Playwright test for the new panel, verified by screenshot instead.
- **Model:** each agent is a separate headless `claude -p` session with its own MCP server process (`SKETCHPACT_AGENT=<id>`), talking to the same canvas server. `npm run debate -- "<question>" [--context file] [--repo dir]` launches both with mandate prompts and prints the URL. Agents only interact through the board and messages at round boundaries; the arbiter sits between them.
- **Ownership is enforced by the tool, not by the prompt:** an agent's nodes land in its own frame, tagged `customData.owner` and coloured; it can rename/remove/move only what it owns, and can `connect` to the opponent's nodes (that's how you propose an interface) but not edit them. Unowned elements are the user's. Removing your own node removes edges attached to it, even the opponent's, and the diff shows it.
- **Attribution in the diff:** `+node x "..." [by simplicity]`; unmarked lines are the arbiter's. Each agent's `yield_turn` result carries the diff since *its own* yield (so it includes the opponent's edits and the arbiter's), the opponent's message, and `skipped` names if the arbiter stopped waiting.
- **Concurrency:** layout is async, so two agents' `apply_ops` could interleave and lose an update. A mutex serialises read-apply-layout-write, plus a version check that retries if the board changed while laying out (a test fires both agents at once and checks all 8 nodes land).
- **Bugs the real run found (again the readability gate's inputs were wrong, not the agents):**
  1. Excalidraw ignores an arrow label's stored position and draws it at the polyline's middle vertex (odd vertex count) or the midpoint of the middle segment (even). My checker validated positions that were never rendered; a label sat on another edge's arrowhead. Fix: choose the spot from real geometry (clear of nodes, notes, other edges, other labels) and insert a vertex plus collinear fillers so that spot *is* the middle vertex. Test: stored label position equals the rendered position within 1px.
  2. The "too large to read" check ignored free-standing notes, so four long notes in a strip made the board 30% zoom and the gate said nothing. Fixed and pinned with the real board as a fixture (`test/fixtures/debate-round1.excalidraw`). The retry of the same debate then showed the gate working: one agent said it kept its board small "because it is at its size limit".
  3. Free-floating labels: giving labels to ELK makes each one its own layer (tall boards). New candidates route without labels and size the gap between layers to fit the largest label.
  4. A test race, not a product bug: two sessions registering concurrently made either agent the scribe; the test now registers sequentially. (In real use the scribe is whoever reaches the server first.)
  5. Own tooling, twice: `pkill -f` patterns matching their own shell, and a two-branch balancing loop with the branches swapped that hung vitest for 4 minutes.
- **The live debate** (vow-lang/vow#1335, "replace ESBMC with a native verifier"): scoped to the four decisions that shape the first cut (solver interface, call semantics, loops, collection model and scope). Both agents read the issue text and grepped the local vow repo before arguing, and cited `file:line`. Outcome: `docs/decisions/0002-...`. Both agents conceded D4/D5 in round one (inline calls, BMC-only), leaving two real disagreements (one seam or none in the encoder; length-only vs array+len strings). The user pressed Agree & finish on turn 1 with no comment.
- **Observations for the post:**
  - *Convergence is fast.* With a passive arbiter, two opposed mandates collapse to nearly the same design in one round, because each agent's honest reading of the evidence (D9 makes ESBMC the oracle) pulls both toward "change one variable at a time". The debate framing surfaced real edge cases (the unwinding assertion, `byte_at` parity, three drifting skip lists) even so. If you want a real fight, the arbiter has to push, or the mandates need to conflict on evidence and not just on taste.
  - *The scribe was honest about the arbiter's silence.* The record states there is no written ruling, that the String model is unresolved (both statements are still on the board), marks which claims were verified and which were not, and even corrects the other agent's citation (`contracts.md:50`, not `:52`). That's the behaviour the skill asks for and it came out without further prompting.
  - Two live sessions produced no revise loop; again the user agreed at turn 1. The revise path (diff-driven response, concessions) remains covered by tests, not by a live run.
- **Display finding (unrelated to M6), root cause found:** the user reported pixelated diagrams and could not find a zoom button. The canvas bitmap is exactly CSS size x devicePixelRatio (measured at 1x and 2x), so the app isn't upscaling. Likely causes: boards fit at 40-50% zoom (1px strokes look jagged; a screenshot enlarged 2-3x shows it) and/or OS display scaling reporting a device pixel ratio of 1. Options offered: raise the fit-scale floor, and write an SVG beside each recorded `.excalidraw`.
- **Known cosmetic:** edges into a cluster can cross the cluster's title text (ELK doesn't know about frame titles); both agents' clusters get drawn stacked, and the arrow between them runs a long way.
- Totals: 137 tests across 12 files; commits per milestone M1-M6 plus the fixes found by real sessions.

### Pixelation and "where is zoom?" (root cause)
- Excalidraw switches to its **phone layout when the canvas is narrower than 730px** and that layout has no zoom controls (`MQ_MAX_WIDTH_PORTRAIT = 730`; measured: canvas 780px shows them, 680px does not). My 320px side panel eats canvas width, so any browser window under ~1050px hits it, and on a tiling window manager (the user runs Hyprland) a half-screen window is ~960px. There is no `formFactor` override in the 0.18 API.
- It compounded with two of my own choices: the board is auto-fitted (40-50% zoom for a debate board, 1px strokes, hand-drawn diagonals look jagged), and I **re-fitted on every yield, erasing any zoom the user did**. So the user saw a tiny board they could not enlarge, then enlarged the screenshot. The bitmap itself was correct (canvas pixel size = CSS size x devicePixelRatio at 1x and 2x).
- Fix: our own Zoom in / Zoom out / Fit buttons in the panel (work in any layout), and the auto-fit now only runs when the user has not changed zoom or scroll since the last fit (compared to a recorded post-fit view). Playwright tests at a 960px window, and one that a user zoom survives a yield.
- Still open: a half-screen window is a small canvas; the readability gate assumes a 1200x850 view. Feeding the real viewport size to the server would make the gate honest but would block more boards; not done.
